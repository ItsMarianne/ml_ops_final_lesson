# housing_mlops

A training pipeline + serving stack for the California housing regression
problem: MLflow tracking/registry, a feature-selection analysis step,
GridSearchCV over three model families, a FastAPI prediction service, and a
small Flask front-end that calls it.

New to this codebase, or to MLflow/Docker/ML concepts in general? Start
with **[docs/WALKTHROUGH.md](docs/WALKTHROUGH.md)** instead — a
plain-language glossary and a suggested file-reading order. This README is
the reference for *why* things are built the way they are; the walkthrough
is the tour for *first* getting oriented.

## Architecture

```
data/raw/california_housing.csv
        |
        v
config/features.yaml  <---  scripts/select_features.py  (correlation +
        |                    permutation importance; run on demand)
        v
src/housing_ml/train.py  --(logs runs, registers, promotes)-->  MLflow
        |                                                       (tracking +
        |                                                        registry)
        v                                                            |
config/train.yaml (experiment/registry names,                        |
hyperparameter grids, promotion rule)                                 |
                                                                       v
                                                          api/main.py (FastAPI)
                                                          serves models:/<registry_name>@prod
                                                                       |
                                                                       v
                                                          webapp/app.py (Flask)
                                                          simple HTML form -> API
```

Everything runs as separate Docker containers on one `docker-compose`
network (`mlnet`): `mlflow`, `trainer` (one-shot batch job), `api`, `webapp`.

## Quickstart

Requires Docker, and [uv](https://docs.astral.sh/uv/) for anything run
locally (linting, tests, the feature-selection analysis trigger). uv is
**only** used locally/in CI -- none of the Docker images invoke it; they
install pinned `requirements.txt` files with plain `pip` (see
"Dependency management" below).

```bash
make sync   # install everything into a local .venv (for lint/test)
make up     # docker compose: start mlflow, run the trainer, start api + webapp
```

Then:
- MLflow UI: http://localhost:5000
- API: http://localhost:8000/predict (POST), http://localhost:8000/health
- Webapp: http://localhost:5001

Run `make help` for the full command list.

## Config-driven, not hardcoded

Two YAML files under `config/` are the single source of truth for anything
you'd otherwise have to edit Python and rebuild an image to change:

- **`config/train.yaml`** — MLflow experiment/registry names, the
  train/test split, the CV settings, and the hyperparameter grid per model
  family. Both the trainer and the API load `registry_name` from here --
  they can't disagree on what the model is called (an earlier version of
  this project had exactly that bug: the trainer registered under
  `housing-regression`, the API looked for `housing-regressor`, and the API
  could never find a model).
- **`config/features.yaml`** — which raw columns actually get trained on.
  Generated by `scripts/select_features.py` (see below), not hand-edited.

## Feature selection

`make select-features` runs `scripts/select_features.py` inside the trainer
image. It screens every raw feature two ways -- Pearson correlation with the
target, and permutation importance from a baseline RandomForest -- and only
proposes dropping a feature if **both** signals agree it contributes little.
It writes the result (with the actual numbers behind each decision) to
`config/features.yaml`, and saves comparison plots to `reports/figures/`.

This is a deliberately manual, reviewable step, not something that runs
automatically on every `make up` -- changing what the model trains on is a
judgment call worth looking at (read the printed numbers, check the plots),
not something that should silently change on every training run.

## Promotion is gated, not automatic

`train.py` doesn't blindly push the newest run's best model to `prod`. For
each alias in `promote_aliases` (`dev`, `uat`, `prod`), the candidate model
is only promoted if it beats whatever is currently aliased there, on
`promotion_metric` (`test_rmse` by default, lower is better) — see
`config/train.yaml`. If an alias has nothing registered yet, the first
candidate always takes it. This is what stops a noisy or unlucky training
run from silently regressing `prod`; skipped promotions are logged with the
metric comparison that caused the skip.

## Prediction logging (seed for future drift monitoring)

Every `/predict` call appends one JSON line (timestamp, input features,
prediction) to `logs/predictions.jsonl` (mounted as a volume so it persists
across container restarts). This module does **not** detect drift itself --
there's no ground-truth feedback loop yet, so there's nothing to check
prediction *quality* against. What it does provide is the raw material a
future scheduled script would need to compare production feature
distributions against the training set (e.g. via PSI or a KS test per
feature) and flag data drift.

## Testing

- **`make test`** — the pytest suite (`tests/`): pure unit tests with no
  network calls, no containers. Covers data validation, feature selection,
  evaluation metrics, the promotion-safeguard decision logic, prediction
  logging, and the API's request/response contract (mocked model).
- **`make smoke-test`** — hits an *already-running* stack
  (`scripts/smoke_test.py`) over real HTTP: mlflow reachable, API health +
  a real `/predict` call, webapp health + a real form submission. Run this
  after `make up`, especially after touching a Dockerfile, docker-compose.yml,
  or anything about how the services are wired together -- it catches the
  class of bug unit tests structurally can't see. Not run in CI (no stack
  is running there).
- **CI** (`.github/workflows/ci.yml`) runs lint + the unit test suite on
  every push/PR. It does not run the training pipeline or spin up
  docker-compose -- a full GridSearchCV run is too slow for every CI run. A
  green CI run means "the code is correct," not "the model trains
  end-to-end" -- `make smoke-test` (or a full `make up`) is still worth
  doing by hand before merging anything that touches the pipeline or
  Dockerfiles.

## Dependency management

`pyproject.toml` + `uv.lock` at the repo root are the source of truth,
managed with `uv` **locally only**. Each service's Docker image installs a
pinned, plain-`pip`-installable `requirements.txt` exported from that lock
(`trainer/requirements.txt`, `api/requirements.txt` — regenerate both with
`make lock` after changing dependencies). `webapp/requirements.txt` is
hand-maintained instead, since the webapp is a standalone HTTP client that
doesn't need any of `housing-ml`'s base dependencies (pandas, scikit-learn,
mlflow, ...).

## Project layout

```
config/            train.yaml, features.yaml
data/raw/          the dataset
src/housing_ml/    shared package: config, data, features, models, evaluate,
                   registry (MLflow logging + gated promotion),
                   prediction_log, train (CLI entrypoint)
scripts/           select_features.py, smoke_test.py
api/               FastAPI service (main.py) + its Dockerfile
webapp/            Flask front-end (app.py, templates/) + its Dockerfile
trainer/           trainer's Dockerfile (runs src/housing_ml/train.py)
tests/             pytest unit tests
reports/figures/   plots from scripts/select_features.py
logs/              predictions.jsonl (gitignored)
```
